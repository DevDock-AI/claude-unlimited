Session routing
How new sessions and their subagents are placed on your accounts
Balance sessions and subagents across accounts
Each new agent starts on the least-busy account. Same as launching every session with --distribute. Off by default.
Go back to your first-choice account when it's free
After a switch, return to the highest-priority account that can serve — but only once nothing has been sent for ten minutes, so no session is moved mid-task. Off by default.
Switch every profile when its Fable limit is spent
Overrides each profile's own "Leave this profile when its Fable limit is spent" switch: while this is on, any account whose Fable weekly limit is spent hands its whole session — every model — to another account. Off by default, and then each profile decides for itself. Never overrides cu code --profile or Take over.
A Claude Code session is not one caller: the agent you type at (the "main agent") and every subagent it spawns send their own requests. Normally they all share one account, chosen by rotation. Turn this on and each new agent goes to the account with the fewest agents already working on it, across all your sessions — ties go to your priority order, then to the least-used account. Over time this spreads your usage across accounts instead of draining one first.
Balancing happens only when an agent starts — a new session, or a new subagent. It never rebalances mid-session: once an agent is on an account it stays there, so its prompt cache stays warm. It moves only if that account reaches its switch threshold or a usage limit, becomes unavailable, or the agent sits idle for an hour. It spreads by how many agents each account is serving, not by usage percentage, so usage evens out roughly rather than exactly.
Setting OFF (default) — one account at a time
Example: you ask Claude Code to audit three services, and it spawns two subagents to read them in parallel. All three — the agent you type at, and both subagents — send their requests to Personal Max. When Personal Max reaches its switch threshold, all three move together to Work Max. This is how Claude Unlimited has always worked.
Setting ON — agents spread across accounts
Example: the same audit, with the setting on. The agent you type at starts on Personal Max, the first subagent on Work Max, the second on Codex — all three at the same time, each on the account that was least busy when it started. Each stays on its own account until it finishes. If Work Max reaches its threshold mid-task, only the subagent on Work Max moves; the other two stay where they are.
Still available per session either way: cu code --distribute turns balancing on for one session while this is off. cu code --profile <name> always wins over both and pins everything to one account. A profile marked "Forced in subagents" still takes every subagent, whatever this is set to.
1M context window
How much conversation a session can hold before it has to compact
Context window for cu code
Auto asks for the full 1M window when a Claude account can take the session; a ChatGPT/Codex account beside it is guarded turn by turn. Off by default it would be 200K.
Auto
Claude Code default
Prefer 200K
Force 1M
Several Claude models hold a million tokens — Sonnet 5, Opus 4.7, 4.8 and 5, Fable 5 and 5.1, Mythos 5 and 5.1. Claude Code only uses that window when it is talking straight to Anthropic; pointed at any other address, including this daemon on your own machine, it falls back to 200K because it cannot tell what is on the other end. For a Claude or Anthropic-API account that caution is unnecessary: the daemon relays to Anthropic with your own credential, so the million really is there. A ChatGPT/Codex account in the same pool is a GPT model with a ~272K window of its own — so the daemon sizes every turn before routing it, sends a ChatGPT account only what fits, and gives longer turns to a Claude account. Auto says so whenever a Claude account can take the session.
Auto stays quiet whenever it cannot be sure: a pool with only ChatGPT/Codex accounts (nothing there holds more than ~272K, so 1M would only mean compacting sooner), an API profile pointing somewhere other than Anthropic, or a Claude Code version this build has not checked. Force 1M overrides all three. Your own CLAUDE_CODE_DISABLE_1M_CONTEXT always wins, and a bigger window does not mean a bigger quota — the same conversation just compacts far less often. The one visible sign of the guard in a mixed pool is a compaction that comes earlier than it would on Claude accounts alone, when nothing but a ChatGPT account is left to take a long turn.
Force 1M sets the window on every session whatever the route — a ChatGPT/Codex-only pool, a pinned ChatGPT account, an API profile pointing elsewhere, even a Claude Code version this build has not checked. The capacity guard stays on: a ChatGPT/Codex account still takes only turns that fit its ~272K, and a turn nothing can hold gets a prompt-too-long so Claude Code compacts. It cannot enlarge a model that is not natively 1M (Sonnet 4.6 and Haiku 4.5 stay at 200K — only the eight native-1M Claude models change), and a backend you pointed it at may reject what the client now sends.

Keep serving on purchased credits
Off by default. Your plan window is already paid for; credits are charged per request.
When a ChatGPT account runs out of its plan window, Claude Unlimited rotates away from it and comes back when the window resets. If you have bought credits on that account, they can carry it through instead — but every request then costs real money, so this stays off until you turn it on. Accounts with no credits are unaffected, and so is every Claude account.

ECO — Efficient Context Optimization
Shorten what tools printed before it is sent, so the same work costs fewer tokens
ECO mode
Off by default. Only text a tool printed is ever rewritten — never your messages, the system prompt, tool inputs, or an error.
Off
Light
Aggressive
What ECO rewrites: only the text a tool printed back — a command's output, search results, a file listing. Sent exactly as written: your messages, the model's replies, the system prompt, tool inputs, and any result marked as an error. Output under 500 characters is never touched. It runs before an account is chosen, so it works the same for Claude, Codex and API profiles.
Light — collapses repetition, keeps every error
Collapses repeated lines and groups long lists. Nothing an error printed is dropped, and every cut leaves a count behind.
Repeated lines
40 identical "retrying…" lines become one line plus "… (39 duplicate lines, ECO)". Logs over 2,000 lines are capped, with the rest counted. JSON and source code are skipped — there, repeated lines are values.
Build and test logs
Every error line is kept, in its original place. The first 5 warnings and 3 deprecation notices are kept; 84 "Compiling …" lines become "Compiled 84 packages". Anything left out is counted.
git status
A count per group — staged, modified, untracked — with the first 10 paths of each, instead of every path.
Search results
path:line matches grouped by file, first 10 per file, e.g. "app.js (37 matches)" followed by 10 of them and "… +27 more".
Aggressive — everything in Light, plus
Also discards detail the model cannot reconstruct. It still names what went, but the text itself is gone.
Very long output
250 lines or more: the first 120 and last 60 lines are kept — what the command was doing and how it ended — with "… +4820 lines truncated (ECO)" in between.
git diff
Each file gets one summary line with its added and removed line counts, such as +42 -7; each hunk keeps its first 100 lines, and the rest is counted.
git log
Each commit's header and message are kept; a diff embedded in the log is dropped.
tree, ls, find
tree is capped at 200 lines. ls -l drops the permission, owner, size and date columns and ends with a count per extension; folders such as node_modules and .git are counted, not listed. find groups paths by folder, 10 names each.
What ECO guarantees
  • The same output is always rewritten the same way, on every turn — so the prompt cache keeps hitting instead of costing more than ECO saves.
  • Never longer, never empty. If a rewrite does not make the output shorter, the original is sent.
  • Every cut says how much went — a count such as "… +27 more" or "(39 duplicate lines, ECO)" — and running ECO again over text it already shortened changes nothing.
  • If anything inside ECO fails, the original request is sent. ECO can never be the reason a request fails.
How savings are counted: the bytes removed are exact, recorded per request. Tokens are estimated from what that same request was actually billed, and cost from that model's input price — Statistics marks both as approximate.
Primitive speech
The model answers in fewer words — every fact kept
Speech level
Off by default. Adds a short instruction to each agent turn, and a one-line reminder to each message you type, so the model's replies cost fewer output tokens. Nothing you or the model already wrote is reworded.
Off
Lite
Full
Ultra
Lite — full sentences without filler: “The token expiry check causes this: it uses < instead of <=.”
Full — fragments, no articles: “Bug in auth middleware. Expiry check uses < not <=. Fix:”
Ultra — as short as stays unambiguous: “Inline object prop, new reference each render, re-render. Use useMemo.”
Always kept exactly: code, commands, file paths, error messages, numbers, and words like not, only and unless. Written normally at every level: files, code comments, commits, documentation, and pull request or issue text. Security warnings and destructive or irreversible steps are spelled out in full sentences. The model is also told not to narrate its own reasoning ("Privately…", "Let me…"). Replies stay in your language.
Applies to every session, subagent and account type, Codex included. Helper calls such as titles and summaries are left alone. The instruction goes after Claude Code's own system prompt, so prompt caching keeps working; changing the level in the middle of a session costs one uncached turn. What it saves is measured from real replies in Statistics.

Which account a session uses
Four ways to decide, in order of precedence
How What happens
cu code --profile <name> Everything in that terminal — main agent and subagents — goes to that one account. Beats every other rule.
Profile menu → "Force in subagents" Every subagent, in every session, goes to that profile; the main agent keeps rotating normally. One profile at a time. If it runs out, subagents spread across the rest.
cu code --distribute The main agent and each subagent start on the least-busy account and stay there, each keeping its own prompt cache warm. No rebalancing mid-session.
Settings → Session routing "Balance sessions and subagents across accounts" makes the line above the default for every session, with no flag. Off by default.
Nothing set (default) Normal rotation: every agent shares the account with the lowest priority number, until it hits its threshold or runs out, then all of them move to the next one.
Context size: several Claude models hold a million tokens, but Claude Code drops to 200K whenever it is pointed at anything other than Anthropic's own address — including this daemon. For a Claude or Anthropic-API account that caution is unnecessary, so cu code asks for the full window back. A ChatGPT/Codex account in the rotation no longer costs you the window: the daemon sizes every turn and keeps any that would overflow a GPT model's ~272K window on a Claude account; when no account can hold it, Claude Code is asked to compact. Settings → 1M context window.
A plan can limit one model on its own weekly clock — you can run out of Fable while the account's own windows still look healthy. Each profile has a switch, "Leave this profile when its Fable limit is spent", off by default. With it on, the moment that account's Fable weekly limit is spent the whole session moves to another account — every model, not just Fable requests — and rotation skips the account until the limit resets or a fresh usage read shows room; it is never marked exhausted. With it off, the account keeps serving and only Fable requests get the provider's limit error. Settings → Session routing → "Switch every profile when its Fable limit is spent" turns it on for every profile at once. ChatGPT accounts are covered through the model mapping: OpenAI only reports whether a model is usable, so a ChatGPT account counts as spent when the GPT model Fable maps to is unavailable. A --profile pin and Take over are honoured regardless, with one Activity line saying the limit is spent; a pinned branch moves for good once another account can take it, and if no account can, the session stays put and you get the provider's own error.
After a switch the pool stays on the new account for as long as it works, even once your first-choice account refills — moving back would throw away a warm prompt cache and could move an agent mid-task. Settings → Session routing → "Go back to your first-choice account when it's free" changes that, and only ever acts after ten minutes with nothing sent.
Calling the daemon from your own app
Anything that speaks the Anthropic Messages API
Point your app's base URL at this daemon and use the local token from Settings → Network as its API key. Nothing else changes.
Claude Code labels every request with the session and agent it came from, and that label is what keeps a conversation on one account. Your app sends no such label, so each request is routed on its own and a batch can land on several accounts, each paying a fresh cache miss. Send a stable id of your own instead, and every request carrying it is treated as one session: it stays on the account it started on for as long as that account can serve it, keeping its prompt cache warm, and rotates only when that account hits its threshold, runs out or becomes unavailable. Give each worker, conversation or job its own id and they spread across your pool.
x-claude-unlimited-session: my-worker-1
Copy
Take over — from here or the HUD — still beats all of it, and holds every request on the account you picked until you release it.
Every request carrying the same id is one branch, and each branch stays on one account while it works — so a batch of workers spreads across your accounts instead of scattering request by request.
Need to know whether the pool is busy — to run a batch job only when nobody is working, for instance — read it from the status endpoint. "idle_seconds" is how long since any account last served a request (null when this daemon has served none yet), and "serving_now" lists the accounts with a request open at this instant. Don't use the "Used now" light for this: it deliberately stays on for 15 minutes after the last request so it doesn't flicker between refreshes.

When every account is out of capacity
What your client is told, and what gets logged
When every enabled account has used up its window, requests are answered with 503 and the message "Claude Unlimited — all profiles are out of capacity", along with the time the first window reopens and a Retry-After header for clients that honour one. It is said once per outage — a single Activity line and a single notification, however many requests are rejected meanwhile — and Activity records "Capacity is back" when an account can serve again.
A pool whose accounts are all disabled or need re-authentication reports "No eligible Profile is available" instead: that is a configuration problem, not a quota one, and the two are never reported as the same thing.
Where everything else happens
Adding and removing Profiles, thresholds, priority, budget caps, Export/Import, and notifications are all managed right here in the Dashboard — not on the command line. The commands above are only for the daemon's own lifecycle.
Statistics
What your accounts actually cost, measured from real requests
Cost and tokens over time, broken down by model, project and account, over ranges from today to all time. Token and request counts come from requests that actually went through the daemon. Costs are estimates: every model is priced at its provider's published list rates, so for a subscription account — Claude or Codex — the figure is what the same traffic would have cost on the API, not money you were billed. "Asked for → served" shows which model each request requested against the one that answered it, which is how a Codex account translating your Claude models becomes visible. An activity grid shows how many calls you made on each day of the range.
ECO
Efficient Context Optimization — fewer tokens for the same work
Claude Code re-sends the whole conversation every turn, so a long tool output is paid for again on every later turn. ECO rewrites what a tool printed into a shorter form before the request leaves your machine. Off by default — turn it on in Settings → ECO, which lists every rewrite each mode makes, with an example. Light collapses repeated lines and groups long lists, keeping every error and leaving a count behind; Aggressive also drops detail the model cannot reconstruct. It never touches your messages, the system prompt, tool inputs, or an error result, and if anything in it fails the original request is sent. Primitive speech, in the same Settings section, works the other way: the model replies in fewer words (Lite, Full or Ultra) while code, commands, errors and numbers stay exact, and files, commits and docs are still written normally.
HUD - Heads-Up Display
macOS only, English only
A floating dock showing every account as a circle with two usage rings: the 5-hour window outside, the weekly one inside (blue, red from 90%). The number under it names its window (5h or w); an account that needs re-auth says Reauth in red. The logo takes the account's colour from the Profiles page. On macOS it installs with Claude Unlimited and starts with you — there is nothing to build. It also adds a menu bar item showing the account currently serving. Drag it anywhere — near a screen edge it pulls onto the edge and docks there when you let go, turning to run along it — and hover a profile for its details. Right-click (or Control-click) a profile to take it over, to enable or disable it, or to choose whether its percentage shows the 5-hour or the weekly window — remembered per profile. The cog sets size, orientation, background and transparency. If you close it, reopen it with the button directly above the language selector, or with `cu hud install`; `cu hud remove` takes it away for good. It only ever talks to 127.0.0.1, and the only two things it changes are Take over and enabling or disabling a profile: the same actions as the Dashboard's, sent with the daemon's per-run security token.
